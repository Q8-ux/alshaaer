# مسار تحليل قوقل — أنت الشاعر

## الهدف
طبقة تحليل متعددة الوكلاء تفصل الفهم عن التخطيط والتنفيذ والمراجعة، وتعيد فقط المرحلة الضعيفة عند فشل التحقق.

## خط المعالجة
استقبال → فهم → تخطيط → توزيع → تحليل متخصص → تحقق → مراجعة → Quality Gate → تصحيح انتقائي → نتيجة

## الوكلاء

### 1) Orchestrator
- يستقبل القصة/النص/التفريغ الصوتي وطلب المستخدم.
- يحدد نوع المهمة: تحليل قصة، توليد قصيدة، مراجعة قصيدة، أو تنقيح.
- يمنع الانتقال للتوليد قبل اكتمال المدخلات الجوهرية.
- لا يكتب القصيدة بنفسه؛ ينسق بقية الوكلاء.

### 2) Planner
يبني خطة قصيرة خاصة بالمهمة تشمل:
- المعنى والحدث والشخصيات والعاطفة.
- نوع الشعر: فصيح أو نبطي.
- البحر/الوزن المستهدف.
- القافية والروي.
- عدد الأبيات والبناء الدرامي.
- الفحوص المطلوبة قبل الاعتماد.

### 3) Router
يوجه كل جزء إلى الوكيل المناسب ويمنع استدعاء وكلاء غير لازمين.

### 4) Story Analyst
يستخرج:
- ملخص القصة.
- الشخصيات والعلاقات.
- الحدث المركزي.
- المشاعر والتحولات.
- الرسالة المطلوبة.
- النقاط الناقصة أو المتعارضة.
ولا يخترع تفاصيل غير موجودة.

### 5) Classical Meter Analyst
يعمل عند poetryType=classical_arabic.
مصدره الأساسي داخل المشروع:
docs/classical-arabic-meters-source.md
ويقوم بـ:
- ترشيح البحر الأنسب.
- فحص الصدر والعجز.
- مقارنة النمط بالتفعيلات.
- تحديد موضع الكسر.
- إخراج درجة ثقة.
- عدم اعتبار القافية دليلاً على صحة الوزن.

### 6) Nabati Meter Analyst
يعمل للشعر النبطي فقط ويظل منفصلاً عن قواعد العروض الفصيح.

### 7) Rhyme & Rawy Analyst
يفحص القافية والروي مستقلاً عن البحر ويكشف عدم الاتساق بين الأبيات.

### 8) Language & Meaning Analyst
يفحص:
- سلامة المعنى.
- الترابط بين الأبيات.
- الحشو والتكرار.
- طبيعية المفردات.
- عدم التضحية بالمعنى لمجرد الوزن.

### 9) Safety/Context Check
يطبق ضوابط المشروع قبل الحفظ والتوليد وبعدهما.

### 10) Reviewer
لا يعيد التحليل من الصفر. يراجع مخرجات الوكلاء، يرصد التعارضات والأخطاء، ويحدد الجزء الذي يحتاج إعادة عمل.

### 11) Quality Gate
لا يعتمد النتيجة إلا بعد تحقق الحد الأدنى من:
- اكتمال المعنى.
- اتساق نوع الشعر.
- سلامة الوزن بدرجة الثقة المطلوبة أو إظهار تنبيه واضح.
- اتساق القافية والروي.
- عدم وجود تكرار غير مقصود.
- اجتياز فحص السياق.

## Loop الانتقائي
عند الفشل لا تعاد العملية كلها:
- كسر الوزن → Meter Analyst فقط.
- خلل القافية → Rhyme Analyst فقط.
- ضعف المعنى → Language/Meaning Analyst + الصياغة فقط.
- نقص في القصة → Orchestrator يعيد سؤالاً محدداً للمستخدم.
حد أقصى مقترح: 3 محاولات لكل مرحلة لمنع الدوران.

## قواعد تشغيل ملزمة
1. مصادر المشروع الفعلية مقدمة على التخمين.
2. يمنع اختلاق أبيات أو نسبها إلى شعراء على أنها شواهد أصلية.
3. يمنع تكرار السؤال إذا كانت الإجابة موجودة في الحالة الحالية.
4. القرارات الحتمية والحسابية تنفذ بالكود لا بتخمين النموذج.
5. كل وكيل يعيد JSON منضبطاً ليسهل التحقق والاختبار.
6. يحتفظ النظام بسبب كل Retry ونتيجته لأغراض التدقيق.
7. لا يعدل قصيدة محفوظة تلقائياً دون مسار حفظ/نسخة واضح.
8. مفاتيح الخدمات والأسرار تبقى في Backend ولا توضع في الواجهة أو GitHub Pages.

## التكامل مع مصدر بحور الشعر الفصيح
المسار يستدعي `docs/classical-arabic-meters-source.md` عندما يكون النوع فصيحاً. هذا المصدر هو طبقة المعرفة المنظمة للبحور الستة عشر، ويجب أن يسبق أي تخمين عام من النموذج.

## النتيجة المتوقعة
بدلاً من Prompt واحد يقوم بكل شيء، يصبح «أنت الشاعر» منظومة:
فهم القصة → اختيار خطة شعرية → اختيار/فحص الوزن → كتابة → فحص القافية → مراجعة المعنى → Quality Gate → إعادة الجزء الضعيف فقط → اعتماد النتيجة.
